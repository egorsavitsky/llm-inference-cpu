# Предварительный нагрузочный опыт от 28 октября 2026 года

**Это прогон с возможным повторным использованием префиксов.** Перед ним тот же сервер участвовал в прерванной попытке с одинаковыми детерминированными входами. Эти числа сохраняются как наблюдения, но не используются для сравнения с новым Pod max_num_seqs=1. Для итогового вывода требуется отдельный повтор max_num_seqs=2 после пересоздания Pod.

Проверены 48 измеряемых запросов и два отдельных прогревочных запроса. Все завершились успешно. [Полные измерения](benchmark-seqs2-2026-10-28.json), [методика и команды](../../docs/benchmark.md).

CPU Intel i5-7300HQ, WSL2, Kubernetes v1.37.0, vLLM CPU 0.27.0, Qwen2.5-0.5B-Instruct revision `7ae557604adf67be50417f59c2c2f167def9a775`. Float32, контекст 1024 токена, max_num_seqs=2, max_num_batched_tokens=1024, OMP_NUM_THREADS=2, KV cache 1 ГиБ. Сервер ограничен 3 CPU/7 ГиБ; отдельный клиент — 1 CPU/256 МиБ на том же узле. Сервер оставался в одном Pod без перезапуска, с политикой model-offline.

Выход каждого запроса — ровно 32 токена; раннее завершение EOS отключено для сопоставимости. Вход посчитан токенизатором сервера и проверен по usage. Длинный вход здесь около 592 токенов, в пределах выбранного окна 1024. По восемь запросов на случай; закрытый цикл с ограничением числа активных клиентских потоков.

Для коротких входов переход от одного клиента к двум увеличил общую скорость примерно на 54%, но медиана полной задержки выросла с 5,34 до 7,20 с. При четырёх клиентах скорость практически не выросла, а медиана TTFT выросла до 7,56 с. Это показывает разницу между общей производительностью и ожиданием отдельного клиента.

Для длинных входов увеличение числа клиентов ухудшило и общую скорость, и задержку в этом прогоне. Один только счётчик клиентов не отделяет влияние очереди, планирования prefill/decode, кэшей, нагрузки CPU и памяти. Следующий опыт должен менять один параметр — max_num_seqs — при сохранении остальной методики; лучшая конфигурация пока не выбрана.

По cgroup у отдельного клиента зафиксированы нулевые oom/oom_kill и максимум около 62 МиБ. У сервера memory.peak около 6,27 ГиБ не вырос относительно начала опыта: этот счётчик охватывает всю жизнь контейнера, а не только тест. memory.current включает также учтённые кэши и разделяемую память. За весь интервал снимков throttled_usec вырос примерно на 2,04 с; этого недостаточно, чтобы объявить квоту CPU единственной причиной задержек.

Первый неполный пробный запуск в служебном Pod с лимитом 64 МиБ завершился OOMKilled; он исключён из таблицы. Завершённый опыт выполнен отдельным клиентом с лимитом 256 МиБ. Восемь наблюдений на случай дают p95, равный максимуму выборки, и не позволяют оценить редкие задержки. Один ноутбук, последовательный порядок случаев, без повторов и контроля температуры; выводы относятся к этим условиям, а не к промышленной нагрузке или качеству ответов.
