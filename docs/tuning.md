# Выбор параметров

В конфигурации оставлен `max_num_seqs=2`. При двух клиентах TTFT короткого входа составил 1,13 с против 5,79 с с лимитом 1; длинного — 7,02 против 11,71 с. Дополнительное место уменьшило наблюдаемое ожидание первого текста. [Полная таблица](../results/benchmark-comparison-2026-10-28.md).

По throughput вывод слабее: между прогонами изменились и контроли с одним клиентом. Одной пары опытов недостаточно, чтобы выбрать устойчивого победителя. Следующая серия должна чередовать порядок конфигураций, повторять случаи и контролировать загрузку и нагрев.

## Если ответ длинный, а вход короткий

Большая доля работы приходится на decode. Разные запросы можно обрабатывать вместе на очередном шаге, поэтому сначала стоит проверить увеличение `max_num_seqs`. Возможный выигрыш в общей скорости нужно сопоставить с задержкой каждого клиента.

Длинные ответы накапливают KV-состояние. `VLLM_CPU_KVCACHE_SPACE` должен вмещать нагрузку, но увеличение резерва само по себе не ускоряет вычисления. Число потоков OpenMP тоже подбирается под CPU-бюджет с запасом для HTTP и служебных процессов. В текущем варианте это два потока при квоте сервера в три CPU.

## Если вход длинный, а ответ короткий

Здесь важнее prefill и `max_num_batched_tokens`. Два входа примерно по 592 токена уже превышают текущий бюджет 1024. При включённом chunked prefill вход разбивается на части и может выполняться рядом с decode других запросов.

Более высокий бюджет позволяет обработать больше входа за итерацию; более низкий ограничивает его конкуренцию с уже идущей генерацией. Менять бюджет стоит отдельно от числа последовательностей и измерять TTFT вместе с общей скоростью. При совпадающих началах входов дополнительно помогает prefix caching.

Параметры описаны в [CPU-документации vLLM 0.27.0](https://docs.vllm.ai/en/v0.27.0/getting_started/installation/cpu/#how-to-do-performance-tuning-for-vllm-cpu) и [разделе про chunked prefill](https://docs.vllm.ai/en/v0.27.0/configuration/optimization/#chunked-prefill).

В выполненных опытах выход всегда равен 32 токенам. Режим генерации сотен токенов отдельно не измерялся; предложения для него требуют своего эксперимента.
