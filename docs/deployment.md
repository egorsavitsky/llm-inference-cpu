# Развёртывание

Проверенная среда — Ubuntu 24.04 в WSL2, Intel i5-7300HQ, 4 логических CPU и около 9,7 ГиБ RAM внутри Linux. Docker уже установлен; при необходимости есть `scripts/install-docker-ubuntu.sh`.

В Windows сначала открыть интерактивную Ubuntu:

```powershell
wsl -d Ubuntu -u root
```

В каталоге проекта выполнить:

```bash
sudo bash scripts/setup-kubernetes.sh
```

Скрипт проверяет доступную память и место на диске, устанавливает Minikube 1.39.0 / kubectl 1.37.0 с проверкой SHA-256. Кластер `ml-inference` запускается от пользователя `mlops`: Docker-драйвер, containerd, Calico, 4 CPU и 8704 МиБ. Команды управления используют явный kubeconfig `/home/mlops/.kube/config`, поэтому исходники могут лежать в приватной домашней папке.

Собираются `ml-inference-service:0.1` и `ml-model-downloader:0.1`. Если образы с этими тегами уже есть, они переиспользуются. После изменения образа его нужно пересобрать и загрузить в Minikube с `--overwrite=true`; иначе внутри кластера останется старая версия.

## Что создаётся

`kustomization.yaml` включает Namespace, Deployment, Service и PVC на 3 ГиБ. ConfigMap генерируется из `config/server.json`. API Secret создаётся со случайным ключом; HF Secret передаётся только загрузчику. Для публичной Qwen-модели HF-токен не требуется. Непустой токен можно передать через файл:

```bash
sudo env HF_TOKEN_FILE=/path/to/private-token bash scripts/setup-kubernetes.sh
```

Загрузчик проверяет размеры и SHA-256 восьми файлов. Готовые файлы сохраняются, повреждённые скачиваются в `.part` и заменяются после проверки. При прерывании незавершённый файл скачивается заново. Сервер получает `/models` только для чтения. Модель занимает около 1 ГБ на диске; несжатые образы — 185 МБ у загрузчика и 7,46 ГБ у сервера.

Одна реплика и стратегия `Recreate` освобождают память старого сервера перед запуском нового. Startup probe допускает долгую подготовку; readiness проверяет `/health`. Даже после готовности первый запрос может быть медленным из-за прогрева.

## Проверка offline-запуска

`check_kubernetes.py` получает ответ через Service и проверяет отказ без ключа/с неверным ключом. Затем он проверяет доступный TCP-сервис, применяет `k8s/offline-policy.yaml`, убеждается в блокировке и пересоздаёт Pod. У нового Pod должны остаться прежний PVC, локальный кэш и рабочий API.

Политика действует и на initContainer. При повреждённом кэше для восстановления нужен разрешённый этап загрузки. Повтор полного сценария временно снимает только политику проекта, затем включает её снова. Обычный `verify_release.py` этого не делает. Calico выбран для применения NetworkPolicy: [описание в Minikube](https://minikube.sigs.k8s.io/docs/handbook/network_policy/).

Отдельная проверка пустого PVC:

```bash
sudo bash scripts/check-fresh-download.sh
```

Она не меняет рабочий `model-files`. После успеха временные Pod/PVC удаляются с проверкой их UID; при ошибке остаются для диагностики. Свежая загрузка и полный запуск vLLM записаны в отдельных отчётах.

## WSL и сеть

В этой среде VPN мешал внешним DNS-запросам из WSL. Для первоначальной установки и скачивания его временно отключали; включали обратно после итогового `SUCCESS` или `ERROR`. Это особенность проверенного компьютера. Работающий сервис и финальная приёмка внешнего интернета не требуют.

`network_diagnostics.py` сравнивает DNS по UDP, TCP и HTTPS в WSL и Pod. Для CoreDNS выбирается только ответивший из Pod upstream; адрес самого CoreDNS исключён. В успешном прогоне использовался DNS WSL `172.31.144.1`. HTTPS-пробы тоже ответили, но штатный DoH-путь CoreDNS в этом прогоне не понадобился. Для него проверена конфигурация версии 1.14.6; сеть Windows скрипты не меняют.

Журналы и статус находятся в `results/local/`. При ошибке сначала проверить `*-status.txt` и время отчёта: результат предыдущего успеха может остаться на диске.

Терминал Ubuntu оставлять открытым: [systemd-службы сами по себе не удерживают WSL](https://learn.microsoft.com/en-us/windows/wsl/systemd/). Остановка Minikube сохраняет данные. Удаление PVC или самого кластера может удалить веса.
