# Образ и логи

## Зависимости

База — официальный CPU-образ vLLM с закреплённым digest. Он содержит Python, CPU wheels и нативные библиотеки. `requirements.txt` перечисляет все 155 установленных Python-дистрибутивов, включая косвенные зависимости.

Сборка выполняет `pip install --no-index --no-deps`, `pip check` и `check_environment.py`. Последний сравнивает полный набор пакетов с lock: лишний пакет, пропуск или другая версия останавливают сборку. Lock рассчитан на этот образ; установка в произвольную пустую Python-среду отдельно не проверялась.

Root нужен при сборке для подготовки каталогов. Рабочий процесс имеет UID/GID `10001:10001`, читает модель из `/models` и хранит временные файлы в `/tmp`. В Kubernetes настройки приходят из ConfigMap, ключ — из Secret.

## Почему отдельный канал событий

Выключение обычного request logging не закрывает вывод ошибок библиотек: в traceback или прямом `print` могут оказаться входные данные. Поэтому `service/launch.py` запускает vLLM с сырыми stdout/stderr, направленными в `/dev/null`.

```text
HTTP → RequestEvents → Unix-сокет → проверка полей → stdout контейнера
vLLM → сырой stdout/stderr → /dev/null
```

`service/middleware.py` отмечает начало и конец запроса без чтения тела ради логирования. Для SSE окончание фиксируется после последней части HTTP-тела. `service/events.py` принимает только разрешённые поля: случайный ID запроса, известный маршрут, метод, статус, длительность и результат завершения. Неизвестный URL записывается как `other`.

Обработчик Python logging отправляет категорию источника и уровень, не форматируя сообщение исключения. Unix-сокет работает внутри контейнера, в том числе с `network=none`.

Цена решения — отсутствие подробных traceback в рабочем журнале. При ошибках остаются HTTP-статусы, события и код завершения; подробный разбор выполняется отдельным воспроизводимым тестом. Очередь событий ограничена, поэтому при перегрузке или аварии возможна потеря записей. Долговечный аудит здесь не реализован.

При SIGTERM управляющий процесс даёт группе vLLM до 25 секунд на остановку, затем завершает оставшиеся процессы принудительно.

## Проверки

Обычная приёмка работающего Kubernetes-сервиса:

```bash
sudo python3 scripts/verify_release.py
```

Она отправляет уникальные маркеры, получает обычный и потоковый ответы, затем проверяет серверный журнал. Должны сохраниться события 200/400/401/404, а текст запроса, ответы и ключ — отсутствовать.

`check_service.py` дополнительно проверяет Docker-образ с `network=none`, подавление прямого вывода/traceback и передачу SIGTERM. Ему нужен сохранённый Docker volume `ml-vllm-lesson-models` с моделью; без этого подготовленного тома используется Kubernetes-проверка выше. `--network=none` при сборке относится к RUN, получение метаданных FROM выполняется отдельно.

[Docker-отчёт](../results/service-verification-2026-10-27.json): 155 совпавших пакетов, UID 10001, 10 пар событий, ожидаемые HTTP-статусы и отсутствие контрольных строк. В нём синтетическая проверка вывода отделена от запросов к настоящему vLLM. [Параметр middleware в vLLM](https://docs.vllm.ai/en/v0.27.0/cli/serve/#--middleware).
