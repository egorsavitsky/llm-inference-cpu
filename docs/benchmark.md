# Нагрузочный тест

Клиент работает в отдельном Pod на том же узле: 1 CPU / 256 МиБ. Для каждого сочетания длины входа и числа клиентов отправляется по восемь запросов. Число активных клиентских потоков — 1, 2 или 4; освободившийся поток сразу берёт следующий запрос.

Входы содержат примерно 64 и 592 токена с chat template. Их длина считается через `/tokenize`, затем сверяется с `usage`. Выход фиксирован: 32 токена, `temperature=0`, `ignore_eos=true`. Это синтетическая нагрузка на скорость. По одному отдельному запросу каждой длины используются для прогрева.

## Метрики

- TTFT — время от начала HTTP-вызова до первого непустого текстового фрагмента SSE. Событие только с ролью assistant пропускается. Это приближение первого токена: в одном фрагменте может быть несколько токенов.
- Latency — время до `[DONE]`. Запуск сервера, токенизация при подготовке набора и прогрев сюда не входят.
- Throughput — сумма реально выданных всем клиентам токенов / время всего случая. Например, 64 токена за 5 секунд дают 12,8 токена/с.

Очередь задач внутри клиента не входит в задержку отдельного запроса, но входит в длительность случая. Статистика включает медиану и p95 по ближайшему рангу. При восьми запросах p95 равен максимуму выборки; для оценки редких задержек этого мало.

## Запуск и смена настройки

Из корня проекта в Ubuntu, с уже готовым сервером:

```bash
sudo python3 scripts/run_benchmark.py --label run-1 --requests 8
```

Для сравнения двух лимитов:

```bash
sudo python3 scripts/set_max_num_seqs.py 1
sudo python3 scripts/run_benchmark.py --label seqs1 --requests 8
sudo python3 scripts/set_max_num_seqs.py 2
sudo python3 scripts/run_benchmark.py --label seqs2 --requests 8
```

Остальные параметры сохраняются. У каждой конфигурации новый Pod, поэтому KV-префиксы предыдущего прогона не переносятся. Измерения начинаются после проверки готовности и прогрева.

## Результаты и прерывание

Скрипт пишет `results/local/benchmark-<label>.json`, а до отправки нагрузки сохраняет UID Pod в `*-session.json`. В отчёте — времена каждого запроса, токены, конфигурация, образ, лимиты и cgroup до/после. Вопросы, ответы и ключи не записываются.

Для каждой попытки нужен новый label. История локальна для этой копии проекта. Если её нет, а сервер уже участвовал в тестах, Pod нужно пересоздать вручную. `--allow-reused-pod` разрешает намеренно прогретый опыт и отмечает его в отчёте.

Завершённые случаи сразу попадают в `.partial` (JSON Lines). При сбое они сохраняются в `*-failure.json`; оборванная последняя строка игнорируется. Общий timeout помечает опыт неполным. У клиента в Pod есть собственный таймер, чтобы остановка kubectl не оставляла его работать дальше.

В первых попытках проявились две проблемы. Лимита 64 МиБ у служебного Pod не хватило — клиент завершился с OOMKilled. После выделения отдельного Pod с 256 МиБ прогоны завершились. Кроме того, повтор после неудачной попытки использовал те же входы в прежнем Pod. Такой результат сохранён в [архиве](../results/archive/benchmark-seqs2-2026-10-28.md), а итоговое сравнение повторено на новых Pod.

[Итоговая таблица и сырые данные](../results/benchmark-comparison-2026-10-28.md). Это по одному прогону на конфигурацию на ноутбуке; температуру, частоту и фоновую нагрузку непрерывно не контролировали. Качество ответов этот тест не оценивает.
